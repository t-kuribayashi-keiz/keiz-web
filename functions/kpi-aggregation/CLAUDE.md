このファイルは、直営+サンズミライ(約149〜150店舗)の月次WEB集客KPI集計についての個別
コンテキストです。ルートの [CLAUDE.md](../../CLAUDE.md) を前提とし、矛盾する場合は常に
ルートCLAUDE.mdを優先する。

`functions/`配下に置いているのは、直営とサンズミライを合算した集計であり、単一ブランドに
閉じないため([functions/ad-spend-tracking/CLAUDE.md](../ad-spend-tracking/CLAUDE.md)と同じ

## 数字の性質(重要)

同じ月の数字に**3つの段階**がある。取り違えると分析が壊れる:

| 段階 | 内容 |
|---|---|
| **中間値** | 月の途中(例: 8/16)時点の累計を日割りで逆算した**見込み**。月内の進捗把握用 |
| **速報値** | 月が終わって全データが揃った時点の数字。KPIの判断に使う |
| **確定値** | 速報値からさらに確定した数字。シート上に「速報値➤確定値で+0.3」等の補正メモがある |

**ダッシュボードに中間値が入ったまま月をまたぐと、未達に見える。** 月初に速報値へ更新する
のがこの集計作業の目的。

## 2026年8月行の実測値(2026-09-03 時点)

2026-09-03に「年間計画・目標」タブを読み取って記録した値。

**この行はまだ中間値。** 8/16時点の累計を日割りで逆算した見込みであり、これから速報値に
差し替えるのがこの自動化の目的。したがって**集客数・UU数の列は答え合わせの基準に使えない**
(抽出が正しくても数字は一致しないのが正常)。店舗数の列(L・M〜O・Q〜S)は下記のとおり
別ソースと突き合わせて裏が取れている。

答え合わせは**既に速報値を入れ終えた過去の月**に対して行う(`--month 2026年7月 --calibrate`)。

| 列 | 値 | 列 | 値 | 列 | 値 |
|---|---|---|---|---|---|
| C HP | 2250 | L 店舗数 | 150 | U SEO,MEO | 1299 |
| D HPB | 2701 | M HPB直営 | 121 | V PPC | 604 |
| E Epark | 180 | N HPBサンズ | 6 | W META | 326 |
| F 紹介 | 589 | O HPBミライ | 8 | X AI | 21 |
| H オフライン紹介以外 | 951 | P HPB合計 | 135 | AB SEO UU | 22212 |
| J オフライン合計 | 1540 | Q Epark直営 | 131 | AC MEO UU | 6246 |
| | | R Eparkサンズ | 8 | AD 自然検索UU | 28458 |
| | | S Eparkミライ | 8 | AE PPC UU | 44697 |
| | | T Epark合計 | 147 | Z PPC店舗数 | 137 |

シートの構造も同時に確定した: **1行目がタイトル、2行目がヘッダー、3行目からデータ**。
2026年8月は34行目で、栗林さんの指定と一致する。ただし行番号は固定で持たず、B列の月ラベルで
毎回探す(下記「合計行を固定で書かない」と同じ理由)。

### ここから分かったこと

- **C(HP集客数)= U + V + W + X** が成立する(1299+604+326+21=2250)。過去の行でも一貫。
- **U・P・T は数式**。データ未入力の2026年9月〜12月の行で、他が空欄のままU・P・Tだけ`0`が
  表示されているため。したがってU列は「どこかから転記する」ものではなく、**書き込んではいけない**。
  未確定事項に挙げていた「U列の出どころ」はこれで解消。
- Y列(HP(META以外))は2026年5月までしか入っておらず、6月以降は空欄。運用上使われなくなった
  とみられるため追わない。

## 設計上の必須要件: 合計行を固定で書かない

栗林さんの指摘(2026-09-02):

> 8月HP(速報値)は集客数がN157、AU157、BB157、BL157です。
> **ただし店舗数が変わったりするとこの位置も変わるので、都度確認が必要です。**

**セル位置をコードに直書きしてはいけない。** 店舗が1つ増減すると合計行がずれ、
合計ではない別の行を読む。**エラーは出ないので、ズレた数字がそのままKPIになる。**

実装では毎回、合計行を動的に特定する(「合計」ラベルの検索、または最終データ行の判定)。
特定した行が本当に合計行かを検証してから値を使い、検証に失敗したら**書き込まずに止める**。

## 速報値タブの読み取り位置(2026-09-03 栗林さん指定)

| タブ | 列 | 内容 | 転記先 | 8月の行 |
|---|---|---|---|---|
| ◯月HP(速報値) | N | 集客数 | C列 | 157 |
| ◯月HP(速報値) | AU | SEO UU数 | AB列 | 157 |
| ◯月HP(速報値) | BB | MEO UU数 | AC列 | 157 |
| ◯月HP(速報値) | BL | PPC UU数 | AE列 | 157 |
| ◯月HPB (速報値) | N | 合計集客数 | D列 | 178 |
| ◯月Epark(速報値) | M | 合計集客数 | E列 | 179 |

**行番号(157 / 178 / 179)はコードに書かない。** 栗林さんからも3タブすべてについて
「店舗数によって変わります」と明示されている。ずれたまま読むと、合計ではない1店舗分の値が
そのままKPIになる(下記「合計行を固定で書かない」)。列は
[data/kpi-source-columns.json](../../data/kpi-source-columns.json)に置く。

合計行の特定は2段構え。(1)「合計」等のラベルがあり対象列が数値の行、(2) 決まらなければ
**対象列の値が「その行より上の数値の合計」と一致する行**。どちらの段でも候補が1つに
絞れなければ停止する。特定できたあとも「合計行の値」と「上の行の合計」を毎回ログに出すので、
ズレていれば照合時に見える。

タブ名も直書きしない。月ごとにタブが増え、括弧が半角/全角で揺れるため、月+媒体+「速報値」の
キーワードで1つに絞り、0件でも複数でも停止する。**`HP`は`HPB`の一部**なので、英数字の
キーワードは前後の境界も見て`8月HPB(速報値)`に当たらないようにしている(形式が同じなので
読めてしまい、HPの欄にHPBの数字が入る事故になる)。

## 広告費シートのHPB店舗数: 店舗名マッチング(2026-09-03)

広告費シートには法人を判別する列が無い。栗林さんの指示:

> 広告費シートで判別する方法はないので、あなたが持っている各ブランドの店舗リストと
> マッチングかけて判別してください。ただし、HPBに掲載するタイミングで店舗名を
> 整骨院→整体院に変えている店舗や、SEO対策として【肩こり・腰痛なら】といった冠文字を
> つけている店舗もあるので、完全一致だけでなくもう少し緩い条件でマッチかけてください。

[scripts/store_matcher.py](../../scripts/store_matcher.py) が担当する。処理:

1. NFKC正規化 → 冠文字(【…】［…］など括弧ごと)を除去 → 空白を除去
2. `針灸`→`鍼灸`(院マスタ内にも両方の表記がある)
3. 院の種別語(整骨院 / 整体院 / 接骨院 / 鍼灸整骨院 / 鍼灸接骨院 / 治療院 …)を1つの記号`〇`に潰す。
   **消さずに潰す**のは「わかば」と「わかば整骨院」を同一視しないため
4. 末尾の`院`/`店`を落とす(「枚方公園院」と「枚方公園」)
5. ここまでで完全一致すれば確定。しなければ類似度(difflib)0.82以上の候補を集め、
   **候補が全部同じグループ(直営/サンズ/ミライ)なら採用**する。店舗まで特定できなくても
   店舗数としては数えられるため。グループがまたがったら判定不能として停止

検証: 院マスタ202院すべてについて、冠文字付き・整体院化・針灸表記・全角空白の6パターンが
正しいグループに当たることを確認済み(`tests/test_store_matcher.py`)。正規化を強くしすぎて
**別グループの店舗が同一視されていないこと**も、マスタ全体の衝突チェックで確認している。

集計サマリー行(プラチナ/ゴールド/PPC/HPB合計 等)は
[data/ad-spend-ignore-rows.json](../../data/ad-spend-ignore-rows.json) で除外する。
**この表にも院マスタにも当たらない行が金額付きで出てきたら、処理を止めて行名を全部出す。**
黙って直営に1件足されても数字は自然に見えてしまい、誰も気づかないため。

## ダッシュボードAG〜AOの算出式(2026-09-03 検証)

⑤は「年間計画・目標」タブで自動計算される1店舗当たりの行を転記する工程だが、転記結果が
妥当かを機械的に確かめられるよう、算出式を突き止めた。2026年8月のダッシュボードの値
(36.2 / 15 / 20 / 1.2 / 8.8 / 2.2 / 4 / 189.7 / 298)と**9項目すべてが一致**した。

| 列 | 指標 | 算出式 |
|---|---|---|
| AG | WEB全体実績 | AH + AI + AJ |
| AH | HP実績 | C ÷ L(店舗数) |
| AI | HPB実績 | D ÷ P(HPB掲載店舗数 合計) |
| AJ | EPARK実績 | E ÷ T(Epark掲載店舗数 合計) |
| AK | SEO集客実績 | (U + X) ÷ L ← SEO,MEO + AI |
| AL | META実績 | W ÷ L |
| AM | PPC実績 | V ÷ L |
| AN | SEO_UU実績 | AD ÷ L ← 自然検索UU(SEO UU + MEO UU) |
| AO | PPC_UU実績 | AE ÷ L |

分母がHPBとEPARKだけ違う(それぞれの掲載店舗数)点に注意。全部Lで割ると数字が微妙に
ずれるが、桁は合うので**目視では気づけない**。

なお2026年6月・7月のダッシュボードの値は、現在の「年間計画・目標」タブの値からは
再現できない。転記後に速報値➤確定値の補正が入ったためとみられる。**8月だけが転記直後で
両者が揃っている**ので、式の検証は8月で行った。

## L列(店舗数)は当面手動(2026-09-03 栗林さんの判断)

> L列(店舗数)の出どころだけはいったん手動にします。自動化は後回しで。

`WRITABLE_PLAN_KEYS`から外してあるので、スクリプトはL列に**一切書き込まない**。
人が入れた値がそのまま残る。ただしL列は⑤の1店舗当たりの計算(AH・AK・AL・AM・AN・AO の分母)に
効くので、**速報値に更新するときはL列も人が見直す必要がある**。中間値のときの店舗数のまま
月末の集客数を割ると、1店舗当たりが実態とずれる。
