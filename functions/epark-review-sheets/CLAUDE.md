# EPARK口コミシート 提出状況管理

各院が毎月EPARKの口コミ投稿シートをGoogle Driveの自院フォルダへアップロードする運用の、
**提出状況を自動集計する仕組み**。ブランド横断の社内機能なので `functions/` 配下に置く。

発端(2026-09-12、栗林さん): 「院数が多すぎて本社も手動管理が大変。フォルダもぐちゃぐちゃに
なってきた。アップロード日を検出して提出状況をスプレッドシートにまとめたい。」

## 運用ルール(業務側)

業務は**2段階**あり、追うべき軸も2つある。混同しないこと。

| 軸 | 誰が | 何をする | Drive上の痕跡 |
|---|---|---|---|
| 軸1 提出 | 各院(現場) | 毎月3枚の口コミシートを自院フォルダへアップ | 院フォルダ配下にファイルが増える |
| 軸2 送付 | 本社スタッフ | 提出を確認し、EPARK担当の**溝口さん**へ送付 | 送付済みファイルを「溝口さん送信済み」フォルダへ格納 |

- 口コミシートは EPARK提供の『EPARK接骨・鍼灸』口コミ投稿シート。**A4片面1枚に1件**
- 提出形態は院によってバラバラ: 紙を撮影したJPG3枚 / スキャンしたPDF1本(3ページ) / 混在
- 「溝口さん送信済み」の中身は**基本的に前月以前**のファイルになる(送付してから格納するため)

### 軸2が課題になっている背景(2026-09-12 栗林さん)

**送付対応の担当者が長期離脱しており、どの月分まで送付が完了しているか本社で把握できて
いない。** そのため、提出状況だけでなく「いつ分まで溝口さんへ送ったか」の復元も必要。

  (親は `13lMjCv2fjCUEKJDg5lqTAsO2NYkpDAKx`)

## 現場の実態(ここを踏まえないと設計を誤る)

院フォルダの中身は統一されていない。実際に確認できたパターン:

| パターン | 例 |
|---|---|
| 年月フォルダ | `2026.7` `2026.6` `2026.5` |
| 院フォルダ直下にファイル直置き | 007.馬橋東口 に `DSC_3026〜3028.JPG` |
| 過去の残骸フォルダ | `旧データ` `溝口さん送信済み` `2024.5画像` `Epark 口コミ　５月` `不備` |
| 拡張子なしのPDF | `2026.9月　EPARK口コミ`(mimeTypeはpdf、titleに拡張子なし) |

**したがってフォルダ名やファイル名から月を判定してはいけない。**
判定に使えるのは Drive の **createdTime(アップロード日時)** だけ。
古いアーカイブフォルダの中身はcreatedTimeが古いので、月次集計では自然に除外される。

### フォルダの modifiedTime は信用しない(重要な罠)

Driveは**子ファイルを追加しても親フォルダの modifiedTime を必ず更新するとは限らない**。

実例(2026-09-12 確認): `064. 小岩蔵前通り` の「溝口さん送信済み」フォルダは
メタデータ上 `modifiedTime = 2024-12-19` だが、中身には **2026-07-23 作成のファイル**が
入っている。フォルダ日付だけ見て「2024年で運用が止まっている」と結論すると**完全に誤る**。

送付がいつまで進んでいるかは、必ず**フォルダの中身のファイルの createdTime の最大値**で
判定すること。

### 送付済み判定に使うフォルダ名(揺れがある)

| 実在する名前 | 意味 |
|---|---|
| `溝口さん送信済み` | 送付済み |
| `溝口さん送信用` | 送付待ち(まだ送っていない) |

**「送信済み」と「送信用」は意味が正反対**なので、`溝口` の部分一致だけで送付済み扱いに
しないこと。スクリプトは `送信済/送付済` → 送付済み、`送信用/送付用` → 送付待ち、
それ以外で `溝口` を含むもの → `溝口(要確認)` と、判別できないものを正直に分けて出す。

### 送付済みフォルダの中身から分かること

`064. 小岩蔵前通り` の「溝口さん送信済み」の実例:

- 中身の createdTime は 2025-08 〜 2026-07 まで連続して存在 → **2026年7月分まで送付済み**
- ファイル名には EPARK側の管理番号＋年月が付いたものが混在
  (`57169178_小岩蔵前橋通り接骨院①②③202510.pdf`、`202603061552.pdf` など)
- ただし命名は統一されておらず `0.jpg` `1.jpg` `①②③.pdf` `口コミ.tif` なども混在
  → **ファイル名からの月判定は不可。createdTime を使う**

## シート枚数の数え方(検証済み)

- 画像ファイル(`image/*`) → **1ファイル = 1枚**
  - 実物を確認: 記入済みの『EPARK接骨・鍼灸』口コミ投稿シートを1枚ずつ撮影したもの
- PDF(`application/pdf`) → **ページ数 = 枚数**(A4片面仕様のため一致)

### PDFページ数の取得方法(2026-09-12 実データ10本で検証)

GASで `file.getBlob().getDataAsString('ISO-8859-1')` して、page tree を正規表現で読む。

```
/\/Type\s*\/Pages[\s\S]{0,300}?\/Count\s+(\d+)/
```

検証したサンプル10本の結果:

- ヘッダは `%PDF-1.3` / `%PDF-1.4` のみ
- **全件で `/Count N` が平文で1回だけ出現**し、`/Type /Page` オブジェクト数とも一致
- **ObjStm(圧縮オブジェクトストリーム)・線形化(`/Linearized`)は1本も無し**
  → PDF 1.5+ の圧縮構造なら平文パースは失敗するが、現状の入稿PDFは全てこの単純形式
- 並び順は必ず `/Type/Pages` → `/Count N`。間に `/MediaBox [0 0 612 792]` が挟まる版あり
  (`<</Type/Pages /Count 3 /Kids[...]>>` と `<< /Type /Pages /MediaBox [...] /Count 3 ... >>` の2系統)

### 速度: 実体を丸ごと落とすと全件スキャンが終わらない(2026-09-12 実測)

最初の実装は `getBlob()` でPDF実体を全部ダウンロードしていた。結果、**4.5分で2〜7院**しか
進まず、158院で3〜7時間コースだった。

`/Type/Pages ... /Count N` の位置を実データ10本で測ったところ、**全件がファイル末尾から
621〜939バイト以内**にあった。そこで Drive API の media エンドポイントに
`Range: bytes=-8192` を付けて**末尾8KBだけ**取得する方式に変更した。

```js
UrlFetchApp.fetch('https://www.googleapis.com/drive/v3/files/' + id + '?alt=media&supportsAllDrives=true',
  { headers: { Authorization: 'Bearer ' + ScriptApp.getOAuthToken(), Range: 'bytes=-8192' },
    muteHttpExceptions: true });
```

実測(ページ数が既知の5本、9.5MBのファイルを含む)で **5/5一致**。9.5MBでも2.3秒。

**この変更は `UrlFetchApp` のスコープ(外部サービスへの接続)を新たに要求する。**
スコープが増えると、**既存の時間主導トリガーは権限不足で失敗し、自動再開チェーンが黙って
止まる**。実際に一度止まった。スコープを増やす変更をしたら、必ず再認可すること。

所要時間の実測(8院サンプル):

| 状況 | 1院あたり | 全158院の見込み |
|---|---|---|
| PDFキャッシュが空(初回) | 30.0秒 | 約79分 |
| PDFキャッシュが温まった後 | 6.2秒 | **約16分** |

ページ数は `_キャッシュ` シートに fileId 単位で保存されるので、**重いのは初回だけ**。

### 読めないPDFが23%ある(2026-09-12 判明、未解決)

8院サンプルのPDF 248本のうち **57本(23%)** でページ数が取得できなかった。
失敗15本の中身を調べたところ、**全件が同一の特徴**だった:

| 項目 | 失敗個体 | 成功個体 |
|---|---|---|
| ヘッダ | **%PDF-1.6** | %PDF-1.3 / 1.4 |
| ObjStm(圧縮オブジェクトストリーム) | あり | なし |
| XRefストリーム | あり | なし |
| `/Count`・`/Type/Pages` | 末尾・**全体とも不在** | 平文で存在 |

PDF 1.6 の別の生成元が、ページツリーを Flate 圧縮したオブジェクトストリームに格納している。
**平文の正規表現では原理的に読めない。** 手法の不具合ではなく適用限界。

失敗個体のファイル名は `①.pdf` `②.pdf` `③.pdf` のように1枚ずつ分かれている例が多いが、
**「だから1ページ」と推測で埋めてはいけない。** 検証中の代替案は、
画像XObject(`/Subtype /Image`)の個数をページ数の代理にする方法
(画像XObjectはストリームを持つのでObjStmに入らず、PDF 1.6でも平文で残る)。
**正解が分かるPDFでの一致率を測ってから採否を決めること**(`validateImageHeuristic`)。

取りこぼし対策として、スクリプトは3段構えにしてある:
1. 上の正規表現
2. `/Count N` の最大値
3. `/Type /Page` オブジェクトの個数

それでも取れなければ `-1` を返し、明細シートに「要確認」として出す(**0枚として黙って
握りつぶさない**)。25MB超のPDFは解析せず要確認扱い(GASのメモリ保護)。

## 実装

- [gas/ReviewSheetTracker.gs](gas/ReviewSheetTracker.gs) — スプレッドシートにバインドして使う
- **Driveには一切書き込まない(読み取り専用)。** ファイルの移動・削除はしない
  - フォルダ整理(直下ファイルを年月フォルダへ移動する等)は**別フェーズ**。
    栗林さんの指示は「まず集計シートだけ」(2026-09-12)
- 6分の実行時間上限対策として、院単位でチェックポイントを打ち、
  4.5分を超えたら `continueScan` を1分後トリガーで自動再開する
- PDFのページ数は `_キャッシュ` シートに fileId 単位で保存し、再解析しない

### シート構成

| シート | 中身 |
|---|---|
| `提出状況` | **軸1**。行=院 × 列=月。セル=提出されたシート枚数。0=赤/1〜2=黄/3以上=緑 |
| `送付状況` | **軸2**。行=院 × 列=月。セル=溝口さんへ送付済みの枚数。＋「送付済み最新月」「未送付疑いの月」 |
| `明細` | ファイル1件=1行。院名・対象月・ファイル名・種別・枚数・アップ日時・置き場所・送付区分・要確認・URL |
| `設定` | ルートフォルダID / 必要枚数 / 表示月数 / 除外キーワード |
| `実行ログ` | 実行の開始・中断・完了・エラー |
| `_状態` `_キャッシュ` | 内部用(非表示) |

`提出状況` の「直下放置」列は、年月フォルダに入れず院フォルダ直下に置かれたファイル数。
フォルダがぐちゃぐちゃになる元なので、この数字が多い院を個別に指導する材料になる。

`送付状況` の **「送付済み最新月」が、担当者離脱で分からなくなっていた「どこまで送ったか」の
答え**にあたる。「未送付疑いの月」は、提出はあるのに送付済みフォルダに同月のファイルが無い月。

### 「未送付疑い」の読み方に注意

この列は機械的な差分でしかない。以下は誤検知しうるので、鵜呑みにしないこと:

- そもそも本社が「溝口さん送信済み」への格納を始める前の古い月は、全部疑いとして出る
- 格納を**移動ではなくコピー**で運用している院・時期があると、両方に出る/片方にしか無い
- 提出が0枚の月は疑いに出ない(送るものが無いため)

まず「送付済み最新月」の分布を見て、**いつ頃から全院一斉に途切れているか**を掴むのが先。

## 全件展開前に実測した前提(2026-09-12、8院サンプル / ファイル949件)

「効率化・精度向上に必要な検証は最小単位で全部やってから横展開する」という栗林さんの
方針で計測した結果。`diagnoseSample` で再現できる。

| 前提 | 結果 | 判定 |
|---|---|---|
| ゴミ箱のファイルが混入しないか | **0件** | OK(`isTrashed()` 除外も実装済み) |
| ショートカットによる二重計上 | **0件** | OK(除外実装済み) |
| Googleネイティブ形式(ドキュメント等)の取りこぼし | **0件** | OK |
| その他形式(動画等)の取りこぼし | **0件** | OK。全ファイルが画像かPDFのみ |
| 画像1ファイル = 口コミシート1枚 | 実物画像で確認 | OK |
| PDFのページ数取得 | 248本中57本(23%)が取得不可 | **NG** → 上記「読めないPDF」参照 |
| 同一シートの二重計上 | **重複疑い28件(3%)** | **NG** → 下記 |
| 1院あたりの処理時間 | 初回30秒 / キャッシュ後6.2秒 | OK(全件16分) |

### 重複: 送信済みへは「移動」と「コピー」が混在している

同名かつ同サイズのファイルが院内の複数パスに存在するケースが 949件中 28件(3%)あった。
8院中5院で発生。つまり本社の格納運用は**移動に統一されておらず、コピーが混じる**。

放置すると同じ口コミシートを提出枚数として二重に数える。対策方針(未実装):

- 院内で (ファイル名 + サイズ) が同一のものをグループ化し、**createdTimeが最も古い1件を原本**、
  残りを重複として `明細` に印を付ける
- **提出状況** は重複を除いて数える
- **送付状況** は重複かどうかに関係なく「送信済み配下に同月のファイルが在るか」で判定する
  (コピー運用の院で送付済み判定が消えないようにするため)
