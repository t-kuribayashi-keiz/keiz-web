# 直営135院 WordPressブログ月次更新の自動化(設計・現状整理)

**背景**: 栗林さんより「直営全店舗に毎月ブログをアップロードしているが手動対応が面倒なので
全部自動化したい」との依頼。現行マニュアル(Googleスプレッドシート「ブログ更新仕様書」
https://docs.google.com/spreadsheets/d/1VjA5jwLLHES1U1RPtO_WhwS0BJJ3sXXSoLx4ah4Ac6k)を
読み込み、関連データソースを調査した結果をまとめる。

**方針確認済み(2026-09-18、栗林さんに確認)**:
- 自動化の到達点: **完全自動(生成から公開まで無人)**
- 原稿ネタ(①〜⑨の元データ)は**各店舗スタッフが毎月手入力する運用のまま**(自動化対象外)。
  自動化するのは「原稿ネタが揃った後」〜「WordPress公開・記録」までの工程。

## 1. 現行の手動フロー(マニュアルより)

1. 「ホームページ用原稿資料」スプレッドシート(別ファイル、ID:
   `1_oJBnhMemCs14J-83VVrqXR3BSgm8KOsJ_dvEgeee-8`、**112MB・多数タブ**)の該当タブから、
   更新する店舗の原稿材料(①〜⑨、テーマにより項目数は変動)を選ぶ
2. その内容と「チャットGPT指示」プロンプト(下記2.参照、景品表示法対応の言い回し変換
   ルール)をChatGPTに入力し、文章を整形
3. 変換後の文章を、店舗のWordPressテーマ系統(`chiryouinbiz`/`chiryou-in`系、または
   `curacion`系)ごとのHTMLひな形の`★★★`部分に差し込む
4. 全店共通のWordPressログイン(ユーザー名・パスワードは元シートに直書きされている。
   **本紙・本リポジトリには一切転記していない**)でログインし、カテゴリ・タイトル・
   パーマリンク等を設定して手動投稿(公開)
5. 「院ブログ更新表」タブ(店舗×トピックのマトリクス)の該当セルに投稿日を記入
6. 例外: 稲毛海岸中央整骨院は「静的」ページのため対象外(この店舗はスキップ)

## 2. チャットGPT指示(文章整形ルール、確認済み・全文)

Claude自身が生成時にこのルールを適用すれば、ChatGPTへのコピペ工程自体が不要になる。

> あなたは整骨院のブログ校閲担当です。入力した記事に対して下記の操作・条件を適用し、
> 集客ブログにふさわしい文章にしてください。
> - 「治療」→「施術」に修正
> - 「改善」→「軽減」または「軽減が期待」に修正
> - 誤字脱字・タイプミスを全て修正
> - 表記のばらつき(言葉・数字)を統一
> - 慣用句・ことわざの誤用を修正
> - 文脈に合わない単語、主語述語の不一致を修正
> - 文末は「です、ます」調に統一
> - 句読点の不自然な点を修正、1文の読点5つ以上は「。」で区切る
> - 断定的な表現は柔らかい表現に、全体的に丁寧な表現に
> - 「効果的」→「効果が期待できる」
> - 「自院」→「当院」、「問診」→「カウンセリング」
> - 誤変換系(「元氣」→「元気」等)を修正
> - 条件: 架空の表現・慣用句・ことわざを使わない/「治療」「改善」を残さない/文章を省略
>   しない/入力にない文章を追加しない/**景品表示法を遵守する**

マニュアル内にも重複ルールとして明記:「改善→軽減」「●●できます→●●の効果が期待できます」
「治療→施術」「断定的表現は柔らかい言い回しに」。**景品表示法遵守が唯一の絶対条件**であり、
自動生成後も最終文面がこのルールに反していないか機械的にチェックする工程を必ず挟む
(治療/改善という語が残っていないか、断定表現が残っていないか等の文字列チェック)。

## 3. データソースの構造(調査で確認できたこと)

「ホームページ用原稿資料」スプレッドシートは112MBあり、このセッションのGoogle Drive
ツール(`read_file_content`)では**全体を読み込めない**(タイムアウト・セッション切断が
複数回発生)。全文検索のプレビュー機能で断片的に取得できた範囲から、以下は確認できた。

### 3.1 「院ブログ更新表」タブ(状況管理)

- 行 = 店舗名(例: 本八幡駅前整骨院、幕張北口整骨院 等)
- 列 = ブログトピック名(院長挨拶、7つの特徴、腰痛、骨盤矯正、肩こり、頭痛、
  スタッフ紹介、各種症状別記事、Q&A記事など、確認できただけで80種以上)
- セルの値 = そのトピックをその店舗がいつ投稿したか(日付)、または
  `記事なし`/`アップ不可`/`閉院`/`※画像待ち`等のステータス文字列
- 「カテゴリー」行 = トピックごとのWordPress投稿カテゴリ(症状系トピックは既定カテゴリ、
  スタッフ紹介等は「当院のこだわり」)
- **自動化での用途**: 「まだ投稿していない(または最も古い)トピック」を店舗ごとに
  特定する起点データ。**この見立てが正しいかは要すり合わせ**(月次で「次に何を書くか」を
  人が決めているのか、単純に空欄埋め・ローテーションなのかは未確認)

### 3.2 トピック別「原稿材料」タブ(①〜⑨の実体)

トピックごとに専用タブがあり、店舗を行として①〜⑨の材料が列に入っている。確認できた
実例(スタッフ紹介、タブ名「【あ行】原稿」= 姓の50音別に分割されたタブの1つ):

```
氏名（漢字）,氏名（ふりがな）,顔写真,画像URL,①出身地,②趣味,③血液型,
④持っている資格,⑤当院のキャッチコピー,⑥施術家になるまでの自分,
⑦新人・修業時代の自分,⑧地域の皆さまへの熱いメッセージ
```

**重要な未確認点**: この列構成はトピックごとに異なるはず(症状記事なら「①症状の説明
②原因③施術の考え方…」のような構成になっているはずだが、80種以上あるトピックタブを
全部は確認できていない)。**トピックごとに個別にスキーマを確認しながら段階的に対応
トピックを増やす設計が必須**(全トピック一括対応をいきなり狙うのは事実確認が伴わず
危険)。

### 3.3 HTMLひな形(WordPress投稿本文の型)

マニュアル内に確認できたのは`chiryouinbiz`/`chiryou-in`系テーマ向けの症状記事用ひな形
(`<div class="kakomi_3">`〜、`★★★`を本文差し込み箇所とする構造)1種のみ。
`curacion`系テーマ向けのひな形、および**スタッフ紹介トピック用のひな形**は未確認
(マニュアル内に「curacionで表示がおかしい場合はこちら」という補足はあったが、
ひな形自体は今回のセッションでは特定できていない)。

### 3.4 WordPressログイン・投稿先

- ログインは全店共通の1組のユーザー名・パスワード(マニュアルに直書き)。
  **CLAUDE.mdの認証情報ルールに従い、本紙・本リポジトリのどこにもこの値は転記していない**
- 店舗ごとのWordPress管理画面URLは「アップ状況一覧」シート(院ブログ更新表と同一、または
  隣接するシートと思われる)の院名にハイパーリンクとして埋め込まれている
- ドメイン系統は`brands/chokuei/CLAUDE.md`記載の通り複数混在
  (`*.chiryouin.biz`/`chiryou-in.biz/<院名>/`/`curacion.jp/<院名>/`/ドリーム法人系の
  `*.chiryou-in.biz`)。**「アップ状況一覧」のURL列を店舗ごとに集約しない限り、
  どの店舗がどのテーマ系統かを機械的に判定できない**

## 4. 提案アーキテクチャ(完全自動・無人公開)

ブラウザ操作(claude-in-chrome)ではなく、**WordPress REST API + Application Password**
による投稿を推奨する。理由:
- SalonBoardと異なりWordPressは標準でREST API(`/wp-json/wp/v2/posts`)を持ち、
  Application Password(WP 5.6+標準機能)があれば認証・投稿・公開までAPIで完結できる
- ブラウザクリックに依存しないため、135院規模でも安定して無人実行できる
- **前提条件を1店舗で検証済み(2026-09-20)、結果は「現状動かない」**: Application Password
  自体は発行できたが、それを使ったREST API認証が401で失敗する(詳細は6章)。
  `Authorization`ヘッダーをサーバー側で通す設定変更が本方式の前提条件になった

実行基盤は、他の類似Skill(`hpb-crm-reconciliation`等)と同様に**Google Apps Script**を
軸にするのが妥当(理由: 対象スプレッドシートが112MBあり、このセッションのDriveツールでは
扱えないが、GASなら`SpreadsheetApp`で対象タブ・対象行だけを直接読み書きできるため
サイズ制約を受けない)。

パイプライン概要:

1. (トリガー: 時間主導型、月1回) 「院ブログ更新表」を走査し、各店舗の「次に投稿すべき
   トピック」を決定(稲毛海岸中央整骨院は除外)
2. 対応するトピック別原稿材料タブから、その店舗の行(①〜⑨)を取得
3. 生成AI(Claude API等)に、原稿材料 + 本紙2章の校閲ルールを渡して本文を生成
4. 生成結果に「治療」「改善」等の禁止語が残っていないか、景品表示法上の断定表現が
   残っていないかを機械チェック(残っていれば公開せず人に差し戻す安全弁)
5. 店舗のテーマ系統に応じたHTMLひな形の`★★★`に生成文を差し込み
6. 店舗のWordPress REST APIに投稿(公開状態)
7. 「院ブログ更新表」の該当セルに投稿日を記録
8. 実行ログを1店舗1行で記録し、失敗店舗だけ人に通知(daily-ops-monitor相当の役割)

## 5. 段階導入計画(全トピック一括ではなく1トピックずつ確定)

いきなり80種類のトピック・135院全部を無人化するのは、3章で述べた通り未確認点
(トピックごとのタブ構成、テーマ別ひな形、REST API可否)が多く、公開ブログに誤った文章
(景品表示法違反表現・破損したHTML)がそのまま出るリスクがある。以下の順で確定させながら
広げる。

- **フェーズ0(完了)**: 現行マニュアル・データ構造の調査、本紙作成
- **フェーズ1(完了、2026-09-20)**: スタッフ紹介用HTMLひな形の確認、1店舗でのWordPress
  Application Password発行・REST API投稿の試験。**結果、どちらも当初想定通りには
  いかないことが判明**(6章参照: スタッフ紹介はブログ投稿ではない/REST API認証が
  現状通らない)。「1店舗分を通しで実行」までは未着手
- **フェーズ1.5(次のアクション)**: 6章のブロッカー2点について栗林さんと方針を確認した上で、
  対象トピックを症状記事系に切り替える、またはサーバー設定変更を依頼する等の対応を行い、
  その後あらためて「院ブログ更新表」→「対象店舗特定」→「原稿取得」→「生成」→
  「禁止語チェック」→「投稿」→「記録」を1店舗分、人が最終確認した上で通しで実行
- **フェーズ2**: フェーズ1で確立したパイプラインを他のスタッフ(50音別タブ全体)に展開、
  さらに症状記事トピックを1種類ずつ同じ手順で追加
- **フェーズ3**: 複数トピック・複数店舗が安定稼働した時点で、月次の完全無人実行
  (GASの時間主導トリガー)に切り替え。`daily-ops-monitor`の対象表にも追加する
  (root CLAUDE.mdのルール通り、本番投入時点で監視対象に足す)

## 6. 今回のセッションで持ち越しているブロッカー

- **HTMLひな形**: 2026-09-20、ローカルセッション(claude-in-chrome)で以下まで確認済み。
  - `chiryouin.biz` / `chiryou-in.biz`系(六実駅前整骨院・五井駅東口整骨院で確認): 3.3節の
    `kakomi_3`ひな形が共通で使える。**ドメイン名(chiryou-in.biz)と`curacion`系テーマは
    別物だった**(当初の想定が誤り)
  - `curacion.jp`系(市川さくら整骨院`curacion.jp/sakura`で確認): `kakomi_3`とは別クラス体系
    (`article-body` > `article-outline` > `section.article` > `article-title` /
    `article-flexbox` / `article-detail` / `article-image`)。既存記事は完成文のみで
    ★★★相当の空プレースホルダーは未確認のまま(別途、未執筆状態のひな形を要確認)
  - **スタッフ紹介トピックはそもそも通常のブログ投稿として存在しなかった**
    (詳細は下記の新ブロッカー参照)。想定していた「HTMLひな形の★★★に差し込んで投稿」
    という前提そのものがこのトピックには当てはまらない可能性が高い
- **【新規・重要】スタッフ紹介トピックの公開場所が不明**: `chiryouin.biz`/`chiryou-in.biz`系の
  2店舗で「当院のこだわり」等の既存カテゴリを全件確認したが、スタッフ個人名のブログ記事は
  1件も無かった。実体はトップページの「スタッフ一覧」セクション→クリックで開く
  モーダル内に、原稿材料スキーマ(①〜⑧)に対応する内容が直接埋め込まれていた。
  このモーダルの中身がwp-adminのどの画面(固定ページ・カスタムフィールド等)から
  更新されているのか特定できず(ACF未導入・カスタム投稿タイプ無し・該当固定ページ無し)、
  **テーマファイルへの直接ハードコードの可能性が高い**。この場合、REST API投稿による
  自動化はスタッフ紹介トピックには原理的に適用できない。
  → **要すり合わせ**: フェーズ1の対象トピックを症状記事系(通常のブログ投稿として
  存在することを確認済み)に切り替えるか、スタッフ紹介の実際の更新経路を別途調査するか
- **テーマ系統の店舗別対応表**: 「アップ状況一覧」のURL列を店舗ごとに集約したものが
  リポジトリ内に存在しない(`data/site-urls.json`は公開HP URLのみでログインURLは
  意図的に除外済み)。加えて上記の通り**ドメイン名だけではテーマ系統を判別できない**ため、
  対応表には実際のテーマ確認結果(HTMLクラス体系)も併記する必要がある
- **【新規・重要】WordPress REST API + Application Password方式は、少なくとも1店舗で
  動作しないことを確認済み**: 六実駅前整骨院でApplication Passwordの発行自体は成功したが、
  それを使った`/wp-json/wp/v2/posts`へのPOSTは401(`rest_cannot_create`)、
  `/wp-json/wp/v2/users/me`ですら401(`rest_not_logged_in`)で、Basic Auth認証が
  そもそも成立していない。GET(公開エンドポイント)は同じ認証ヘッダーでも200で返り、
  ログイン中ブラウザのCookie+Nonce認証では同じREST APIが正常に動作したことから、
  **サーバー(Xserver)が`Authorization`ヘッダーをPHPに渡していない**という、共有ホスティングの
  既知の問題が濃厚(有効化しているセキュリティプラグインは無し)。4章の提案アーキテクチャは
  **`.htaccess`等でAuthorizationヘッダーを通す設定変更が前提条件**になる。この設定変更は
  実装担当だけでは完結せず、サーバー管理者側の対応が必要な可能性がある
- **「ホームページ用原稿資料」が112MBある理由**: 画像や長年の履歴が蓄積している可能性が
  高く、GAS実行時のクォータ(実行時間6分等)に影響しないか要検証

## 7. 認証情報の扱い(CLAUDE.md遵守事項の再確認)

- WordPress共通ログイン・Application Password・Anthropic API keyのいずれも、
  **このリポジトリにコミットしない**。GASならScript Properties、GitHub Actionsなら
  Secretsに格納する
- 元マニュアルに書かれていたWordPressパスワードは、本紙を含めリポジトリ内のどのファイルにも
  転記していない
