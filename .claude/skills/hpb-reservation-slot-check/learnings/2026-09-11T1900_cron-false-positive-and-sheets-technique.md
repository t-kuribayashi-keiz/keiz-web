## 事件の経緯: cronの遅延実行が「データが壊れる」実害を初めて出した

これまで`references/github-actions-ops.md`は「cronが13:07 JSTから4〜5時間遅れる」ことを
"運用目的(15時前に気づく)を満たせない"という**間に合わなさの問題**として記録していたが、
2026-09-11に**データの信頼性そのものを壊す実害**が確認された。

- 13:23 JST頃の手動実行: ○111 / ✕26 / ?5(正常)
- 同日17:52 JSTの**遅延した定期実行**が自動的に上書き: ○16 / ✕121 / ?5

原因は仮説だが、**当日PMの経過済み時間帯を、遅い時刻に実行すると「予約不可(過ぎた時間だから)」
と誤って✕判定してしまう**という、既存の設計(`default_date_window()`が当日PMを窓の起点にする)
と「遅延実行」が組み合わさった結果と考えられる。この誤検知は、栗林さんが「バツの数が
めっちゃ増えたように見える」と気づいたことで発覚した(こちらからは能動的に検知できていない)。

**対応**: 2026-09-11、`schedule`トリガーを一時停止した(`workflow_dispatch`のみ残す)。
再開する際は、この誤検知の原因(遅延そのもの、または当日PM起点の窓設計)が解消されたことを
確認してから。

## K/L列の復元手順(今回使った実例)

誤ったデータで上書きされたK3:L144を、直前の正しい実行(GitHub Actionsのrun log)から復元した:

1. `gh run view <run-id> --log` でログを保存
2. ログの`🔍 解析中 (i/142): 店舗名`と`  -> 結果: 判定 (詳細)`のペアをスクリプトでパースし、
   `K列詳細\tL列判定`のTSVを142行分作る(**手作業で書き写さない**。後述の理由)
3. PowerShellの`Set-Clipboard -Value $content`でOSクリップボードに直接流し込み、
   ブラウザ側でK3セルを選択して`Ctrl+V`で一括貼り付け

## 重大な事故未遂: 手作業でJSON配列に書き写すと行が欠落する

142行のTSVを、一度Read toolで読んでからJS配列リテラルとして手で組み立てて
`navigator.clipboard.writeText()`に渡したところ、**142行のはずが134行しか書き写せていなかった**
(8行分が黙って抜け落ちていた)。これに気づかず貼り付けていたら、**K3以降の全行が
8行分ズレて誤った店舗に紐づく**という、視認しにくい重大なデータ破損になっていた。

**教訓**: 100行を超えるような機械的なデータ変換(TSV→JS配列など)を、Read toolの出力を見ながら
手で組み立て直すのは危険。**必ずスクリプト(Python等)に変換させ、行数を`len()`等で機械的に
検証してから使う。** 今回は「142行のはずが134行」に気づけたのは幸運で、件数チェックを
習慣化していなければ気づかないまま貼り付けていた可能性が高い。

## Google Sheetsの行番号特定は、視覚的なスクリーンショット読み取りに頼らない

M/N列(店舗ごとの原因分類)を書き込むには、店舗名から実際の行番号を特定する必要があったが、
以下の方法はいずれも信頼性が低く、大きな時間ロスと複数回の誤読(行のズレ)を招いた:

- **`Ctrl+F`(検索)は、このセッションでは一貫して機能しなかった**(`0/0`件ヒット、
  または前回の検索結果のまま更新されない)。原因は特定できていないが、素直に動くことを
  前提にしないこと。
- **スクリーンショットを見て行番号を目で数える方法は、同じ画面を2回撮っても読み違える。**
  実際に「弁慶はりきゅう整骨院」の行を最初row12→次にrow11と読み違えた、「新潟寺尾東」を
  79/80で読み違えた、「二条駅前」と「二和向台駅前」という別の店舗を混同した、など、
  1回のセッション内で複数回の読み違いが発生した。フォントサイズが小さい・行が詰まっている
  ほど誤読しやすい。

**信頼できた唯一の方法**: 名前ボックス(Name Box)に`A<行番号>`と入力してEnterで移動し、
`zoom`で数式バー(formula bar)のテキストをその場で確認する、を1行ずつ繰り返す。
これは遅いが、**外れたことが一度もなかった**。今回はこれで26店舗ぶんの行番号を
1つずつ確定させて初めて、書き込みを安全に進められた。

**次回への示唆**: 行数がある程度(数十行)ある場合、視覚的なスクロール確認は「あたりをつける」
用途に留め、**実際に書き込む前に必ず名前ボックス+数式バーで1行ずつ確定させる**運用にすること。
また、Google Sheetsのセルグリッドはcanvasベースで描画されており、**`document.querySelectorAll`等の
DOM走査では中身が全く取れない**(名前ボックスや数式バーのような専用UI要素は通常のDOM/input
なので`document.querySelector('input.waffle-name-box')`等で読める)。この違いを知らずに
DOM走査で行データを拾おうとすると時間を無駄にする。

## ✕/○の文字が`type`アクションで欠落する問題、クリップボード競合への対処

`.claude/skills/hpb-salonboard-update/learnings/2026-09-11T1900_groupTop-click-root-cause-found.md`
に詳細を記録した。要点だけ再掲:

- `computer`ツールの`type`で✕(U+2715)・○を打つと無音で欠落する。**必ず実クリップボード
  経由のコピー&ペーストを使う**(`navigator.clipboard.writeText()` → `readText()`で
  直後に検証 → `ctrl+v`)。
- クリップボードは栗林さんの実PCでの他の作業と共有されており、頻繁に上書きされる。
  **貼り付け前に`readText()`で検証、貼り付け後も対象セルを読み返して検証**、を省略しないこと。
- 長い日本語文字列は、セル移動直後に即`type`すると先頭側が欠落することがある。
  `F2`→`wait 1秒`→`type`の順にすると安定する。
