# グッド・スマイル 集客レポート(月次)

毎月の定例作業。グッド7院・スマイル11院の集客状況を単一HTMLアーティファクトにまとめ、
既存のArtifact URLを更新する。

**Artifact URL: https://claude.ai/code/artifact/4696ebe8-e873-497b-911d-197c07437ac9**
(タイトル「グッド・スマイル 集客レポート」。月が変わっても同じURLを更新する。ハブ
ページ https://claude.ai/code/artifact/... 「集客レポート ハブ」からもリンクされている)

設計の前提は [brands/smile/CLAUDE.md](../../../brands/smile/CLAUDE.md)・
[brands/good/CLAUDE.md](../../../brands/good/CLAUDE.md) が正。このスキルは"手順"と
"レポートの固定ルール"に絞る。**このファイルは2026-09-09、初回作成(2026年08月号)で
栗林さんから受けた一連の修正指示をすべて反映して書いた。次回作成時は、ここに書いた
チェックリストをなぞれば同じ手戻りを繰り返さずに一発で出せるはず。**

## 実装資産(このリポジトリに常設)

- **ジェネレータ本体**: [scripts/good_smile_report_gen.py](../../../scripts/good_smile_report_gen.py)

  `python3 scripts/good_smile_report_gen.py --data data/good-smile-report-data.json --out <出力先>`
  で実行する。HTML構造・CSS・チャート描画JS(`renderMultiEntityChart`・`renderYearChart`・
  `layoutLabels`)はここにすべて入っている。**月次更新は基本的にこのスクリプトを直接
  編集せず、`--data`のJSONを更新するだけで完結する**設計。セクションを新設・変更する
  ときだけスクリプト側を触る
- **データ**: [data/good-smile-report-data.json](../../../data/good-smile-report-data.json)
  (`_meta`に当月号・更新方針のメモあり)。**月次で当該月のデータ点を追記する。過去月を
  書き換えない・欠損月を推測で埋めない。** スキーマは下記「データソースとJSONの対応」参照

## Non-negotiable rules(全ブランド共通、docs/chart-conventions.mdへのリンク)

いずれも [docs/chart-conventions.md](../../../docs/chart-conventions.md) に記録済みの
全ブランド共通方針。**新しい指標を追加するときも必ずこの形で出す。「まず簡易な表で出して
後で直す」をやると栗林さんの二度手間になる(2026-09-09、広告実績を単月スタティック表→
時系列に作り直した実例がある)。**

1. **指標は「1店舗あたり」で表示・議論する**。合計値は補足程度。
   **分母(実施院数)は月によって変わりうる。定数(例: 常に11院)で割らない**。
   広告実績のように月次で「担当院数」的な実測値が別途シートにあることがあるので、必ず
   確認してから割る(下記「学習ログ」参照)
2. **時系列グラフは暦月(1〜12月)を横軸にし、年度ごとに1本の折れ線として重ねる**
   (最新年=実線・強調、前年=点線・控えめ)。月を単純に連結した1本にしない
3. **ブランドを合算・一本化しない**(グッド+スマイル合計/平均を作らない)。同じ図に
   複数ブランドの系列を並べて重ねるのは良いが、合成した1本の線・1つの数値にしない
4. **前年同月・前月には数字ラベルを直接つける**(グラフは前年同月比・前月比を見るための
   もの)。単年のみでデータが無い系列は前月ラベルのみ(前年同月は付けない)
5. **オフライン等、自社のWEBチャネルではない参考値はボトルネック診断の対象にしない**
   (季節傾向の参考値としては表示してよいが、「最大のボトルネック」候補には含めない)

## 月次の流れ

### 1. データ取得
上表の出所から当月分を取得し、`data/good-smile-report-data.json`に追記する
(`scripts/sheets_smoke_test.py`をGitHub Actions(`sheets-smoke-test.yml`)経由で実行し、
`mcp__github__get_job_logs`でログを読む。列を絞り込みたいときは`--grep-col`/`--grep-values`、
式を確認したいときは`--value-render-option FORMULA`)。

**列インデックスの読み違いに注意。** このレポート初回作成時、列を1つ読み違えたまま
気づかず先に進みかけたことがある。**小さく明示的な範囲(例: `A4:N4`)を単独で取得して
値を目視確認する**か、**シート側に合計行がある場合は自分で店舗別に積み上げた値と
突き合わせて完全一致するか検算する**(広告費の実例: 11店舗の合計を自分で積み上げたら
シートの「五箱　計」行と¥477,641で完全一致し、列位置の正しさを確認できた)。

### 2. 施策担当エージェントへの分析依頼
`smile-marketing-strategist` / `good-marketing-strategist` に「全体分析を踏まえてボトル
ネックと示唆出しを」依頼する。プロンプトに以下を明示する:
- 前年同月比で悪化している媒体を特定すること
- **オフラインはWEBマーケティングの対象外。季節傾向の参考値としてのみ扱い、
  「最大のボトルネック」候補に含めないこと**(ルール5)

### 3. レポートの再構築・公開
`data/good-smile-report-data.json`を更新したら:
```
python3 scripts/good_smile_report_gen.py --out <scratchpad>/good-smile-report.html
```
生成したHTMLを、既存のArtifact URL(冒頭記載)に`Artifact(action:"publish", url:...)`で
上書き公開する(新しいURLを作らない)。**公開前に一度だけPlaywrightでスクリーンショットを
撮り、新規・変更したチャートのラベル衝突が無いか確認する**(下記「学習ログ」のバグ参照)。

**`label`パラメータに必ず当該の年月号(例: `"2026年09月号"`)を入れて公開する。**
Artifactは同じURLに上書きしてもバージョン履歴(版履歴・バージョンピッカー)として
過去の版が残る仕組みだが、`label`を付けないと履歴上でどれが何月号か見分けられない
(2026-09-09、初回公開時にこれを付け忘れたまま何度か上書きしてしまい、あとから
気づいて再公開でラベルを付け直した)。**過去レポートは消えるわけではないが、
月次で作業するときは必ず`label`で識別できる状態にしておくこと。**

なお、レポートが表示する数値そのもの(暦月×年度の時系列)は`data/good-smile-report-data.json`
にも累積されており、これはGitでコミット・履歴管理されている。**Artifactの版履歴とは
別に、実データはGit側にも残る**(二重の保全になっている)。

### 4. ブランドCLAUDE.mdへの記録
その月に判明した新しい事実・データギャップ・訂正は`brands/smile/CLAUDE.md`
`brands/good/CLAUDE.md`に追記してコミット・プッシュする(このスキル自体は"型"のみを
持ち、ブランド固有の実データ・経緯は書かない)。

## 学習ログ(2026-09-09、初回作成時に踏んだ轍)

今後同じ手戻りをしないための実装上の注意点。**次回このレポートを触るセッションは、
新しい種類の変更をする前にここを読むこと。**

1. **チャートの数字ラベルは「実測」でしか衝突判定できない。** フォント幅を係数で
   見積もって衝突回避しようとしたら、実際のレンダリングフォント(headless Chromiumで
   `ui-monospace`が無い環境ではフォールバックフォントになる)と幅がずれて破綻した。
   `layoutLabels()`は必ず`<text>`要素を実際にDOMへ追加してから`getBBox()`で実測し、
   その実測値で重なり判定・y方向にずらす処理をする(`scripts/good_smile_report_gen.py`
   の`layoutLabels`関数を参照。他のグラフを自作するときもこの実装をコピーして使う)
2. **flexコンテナの直下に、生のテキストノードとインライン要素(`<b>`等)を混在させると
   壊れる。** `.brief-row`(好調/課題/対策の1行)を`display:flex`にした状態で
   `<span class="tag">...</span>好調なテキスト<b>+25.7%</b>続き` のように書いたら、
   テキストノードと`<b>`がそれぞれ別のflexアイテムとして扱われ、行が分断されて
   意味不明な折り返しになった。**flexコンテナの直下に置く要素は、テキスト部分を
   必ず1つの`<span>`で包む**(`<span class="tag">...</span><span>好調なテキスト
   <b>+25.7%</b>続き</span>`)
3. **「1店舗あたり」の分母は、シート側に実測値があるなら必ずそれを使う。** 栗林さんから
   「6月は2店舗、7月以降は5店舗のはずだが、ちゃんとその数で割っている?」と指摘されて
   気づいた。広告データのシートには「担当院数」という行(絶対行124)が別途あり、
   月によって出稿院数が変わっていた(Google: 13院→11院、META: 2院→5院)。**新しい
   指標を「1院あたり」に変換するときは、まず分母のシート上の実測値の有無を確認する。
   無ければ`data/clinics.json`の有効店舗数を使うが、この場合も「その月に本当にその
   店舗数が稼働していたか」を一度は疑う**
4. **新しい指標は最初から時系列(暦月×年度重ね)で作る。** 単月のスタティック表を
   先に出して「時系列にして」と後から言われる、という手戻りが広告実績で発生した。
   ルール2は「後から直す」ためのものではなく「最初から従う」もの
5. **レポートのセクション順序は固定**(上記「レポートの構成」参照)。「データの
   扱い注記」callout を先頭に置きたくなるが、栗林さんの指示で**サマリーが先頭・
   注記は末尾**と確定している。新規セクション追加時もこの順序を崩さない
6. **サマリーの「好調」「課題」に入れる数値は、必ず前年同月比の実測値を使い、
   下部のボトルネック診断セクションと同じ根拠数値にする。** 適当な要約文にせず、
   両方のセクションで数字が一致しているか公開前に見比べる
7. **店舗別のデータで「全体」のように見える行が、実は関連ブランド以外も含んでいたり
   逆に集計範囲が狭かったりすることがある。** 直営の「全体」行は「関西」行より
   データが古い月までしか無かった(2026-08時点)。指示された行をそのまま使う前に、
   本当にその行がブランド・対象範囲・データ範囲の点で指示の意図と一致するか確認し、
   食い違いがあれば黙って合わせず報告する
