# Background

## Why this exists

The user records audio internally on DJI Mic Mini 2S units (likely for staff/customer interactions at their salons — the exact use case for the recordings wasn't stated, only the transport problem). The starting request was simple: connect the Mic to a PC over USB-C and have its recordings end up in Google Drive automatically, without a manual drag-and-drop every time. The user specifically asked whether device identification could happen "the moment it's plugged in" — i.e., zero manual steps per use.

## How the design was decided

The assistant broke the problem into two independent pieces from the start: (1) Google Drive for desktop already turns "put a file in this local folder" into "it's in the cloud," so the automation only needs to solve getting files into that local folder; (2) a DJI Mic Mini 2S, once connected via USB-C, presents to Windows as an ordinary USB mass-storage drive — so "detect the Mic and copy its files" is really "detect a specific removable drive and copy its files," a well-trodden problem (WMI/Task Scheduler device-connect triggers, `robocopy`).

The interesting design question turned out to be *how to identify which physical Mic is which*, because the user's operation isn't single-mic/single-PC — mics get issued to individual staff, and get physically migrated between store locations as the rollout progresses. Two identification strategies were weighed head-to-head in a comparison table shown to the user:

- **USB serial number** (read from `Win32_DiskDrive` via WMI): zero manual setup per mic, but the assistant flagged a real unresolved risk — some manufacturers ship USB controllers that return an identical or blank serial across every unit of the same model, and DJI's behavior here was unconfirmed. The plan was to verify this by asking the user to physically connect a Mic to the PC being used for the build.
- **Volume label** (the drive's display name, set manually once via Explorer rename): 100% reliable because it's a value the operator chooses and controls, at the cost of one manual rename step per physical mic.

That verification never actually happened — no physical Mic was available on the build PC during the session (confirmed by the assistant checking for a connected DJI device and finding none, alongside also finding no Google Drive for desktop sync folder configured on that machine yet). The decision that actually resolved which method to use came from a different angle: the user asked a follow-up question about what happens when a Mic is transferred to a new store, given that the PC it's plugged into will then be a different, unrelated machine. The assistant's answer — that a volume label lives in the Mic's own onboard storage and is therefore already PC-independent, requiring no re-setup on transfer — showed that the "manual labeling" downside of the volume-label approach is a one-time, per-mic cost that's paid once ever, not a recurring one that fights against the multi-store rollout. Given that, and given the unresolved serial-number reliability question, the user confirmed proceeding with implementation on that basis ("はい、お願いします"), and the shipped scripts use volume label exclusively — there's no serial-number code path in the final build at all.

A second table was produced at this point (design-decision only, not re-litigated later) walking through what changes vs. doesn't change on store migration: Mic relabeling — not needed; Google Drive for desktop + the monitoring script — needed once per *new PC* (not per mic); the label↔staff↔folder mapping table — reusable as-is if kept in one shared location, so a store/staff change becomes a one-line edit rather than a redeployment.

## What got built

With the design confirmed, four files were produced in one pass: `config.json` (the mapping table, seeded with placeholder example data — `STAFF_TANAKA`/`田中` and `STAFF_SUZUKI`/`鈴木` — not real store data), `Upload-DjiMic.ps1` (the worker script), `Install-ScheduledTask.ps1` (the one-time installer), and a Japanese `README.md` covering setup and future-store rollout. During this build, a real bug surfaced and was fixed: saving the `.ps1` files as plain UTF-8 without a byte-order mark caused Windows PowerShell 5.1 to misinterpret the encoding as Shift-JIS, corrupting the embedded Japanese log/error strings. This was caught and corrected within the same session (re-saved as UTF-8 with BOM), and the corrected scripts were confirmed to log Japanese text correctly afterward.

The assistant then ran `Upload-DjiMic.ps1` on the build PC to sanity-check it. Since neither a real Mic nor a real Google Drive sync folder was present, the only path actually exercised was the "Drive folder not found" warning branch — which logged correctly and cleaned up its lock file as expected. The assistant was explicit in its final summary that the real copy path (detecting a mic by label, running robocopy, landing a file, seeing it sync) remains unverified and must be checked by the user on an actual store PC.

The assistant also deliberately did not run `Install-ScheduledTask.ps1` even on the build PC, describing it as a "system settings change"-class operation that should be left for the store PC / the user to execute themselves — consistent with treating scheduled-task registration as something outside what an assistant session should do unilaterally, even in a test context.

## Open items / things a future session should not assume are settled

- Whether DJI Mic Mini 2S units actually return non-unique or blank USB serial numbers was never empirically confirmed either way — the volume-label decision was made for the store-migration reasoning above, not because serial numbers were proven unreliable. If a future need arises to identify mics without a manual labeling step (e.g., very high mic turnover), it would be worth actually testing serial-number uniqueness with real hardware rather than assuming the original caution still applies.
- The end-to-end happy path (real mic → real robocopy → real Google Drive sync) has never been observed by the assistant in any session to date. Anyone extending this skill should ask whether it has since been confirmed working on a real store PC before assuming the shipped design is bug-free in practice.
- No recurring-cost logging (time/effort per store rollout) was set up or discussed for this workflow in the original session, unlike the user's established `hpb_work_log.csv` convention for SalonBoard work. If the user wants deployment effort tracked the same way, that would need to be set up fresh — it is not something this skill currently does automatically.
